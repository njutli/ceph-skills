# RGW 逻辑实体与 RADOS 对象映射解析

## 1. 我的理解与疑问
**理解**:
> “对象存储”中的“对象”是用户自定义格式的一个存储单元；
> “RADOS对象”中的“对象”是 Ceph 集群中的数据组织形式；
> “对象存储”中的 **用户**、**存储桶**、**对象**，都是以“RADOS对象”负载的形式存储在“RADOS对象”的 **数据部分**、**扩展属性** 或者 **omap** 中的。

**疑问 1**:
> 这么理解对吗？

**疑问 2**:
> 书中提到“用户上传的数据被切分存放在 RADOS 对象的 Data 部分”，这是不是意味着一个用户对象，是可能分片存储在多个 RADOS 对象中的？

---

## 2. 分析与验证

### 2.1 疑问 1：逻辑概念物理化
**结论**: 这种理解**非常准确**，这正是 Ceph RGW 架构设计的核心——**逻辑概念物理化**。
RGW 中的各种逻辑实体（用户、存储桶、对象元数据）本质上都是通过底层的 RADOS 对象来承载的。

**具体对应关系如下**:
*   **用户 (User)**:
    *   **形式**: 对应 RADOS 池中的一个对象（对象名通常为 user ID），该对象通过二级索引（access_key, swift_keys, email）进行查找。
    *   **存储内容**: 该对象的 **Data 部分**存储了序列化后的 `RGWUserInfo` (包含密钥、配额、子用户等)。
*   **存储桶 (Bucket)**:
    *   **形式**: 对应 RADOS 池中的一个对象（对象名包含 Bucket ID）。
    *   **存储内容**: 该对象的 **Data 部分**存储了 `RGWBucketInfo`（包含拥有者、索引分片数等）。
    *   **索引数据**: 存储桶下的对象列表（索引对象）也存放在单独的 RADOS 对象中，通常位于数据部分或 omap 中。
*   **对象 (Object)**:
    *   **数据**: 用户文件数据存放在数据对象的 **Data** 部分。
    *   **元数据**: 对象的属性（大小、类型、ETag、ACL 等）通常存储在对应 Head RADOS 对象的 **xattr (扩展属性)** 或 **omap** 中。

---

### 2.2 疑问 2：大对象的分片存储机制
**结论**: **是的，完全正确。**
这是 RGW 为了应对大对象存储而设计的核心机制。一个逻辑上的“用户对象”在底层被拆解为一组 RADOS 对象。

**具体拆分类别 (基于源码 rgw_object 和 Manifest)**:
1.  **普通上传的内部切分 (Whole Object Upload)**:
    *   为了防止单个 RADOS 对象过大导致内存压力（OSD 写入时需加载到内存），RGW 会自动切分数据。
    *   **Head (Shadow_0)**: 以应用对象名命名。存储文件开头的一小块数据（默认 `rgw_max_chunk_size`，约 4MB），以及所有的**元数据**。
    *   **Shadow Objects**: 文件剩余数据被切分成名为 `shadow_...` 的多个 RADOS 对象。
2.  **显式分段上传 (Multipart Upload)**:
    *   当文件超过 5GB 或客户端主动分段时，文件被切分成多个 Part。
    *   每个 Part 内部再按 `stripe_size` 切分。此时一个 User Object 对应的 RADOS 对象数量会更多。

**映射关系图示**:
```text
用户对象 (User Object) [逻辑层]
    |
    |--- Manifest (清单/映射表)
         |
         +------ Head RADOS Object (Data: 头部数据, Xattr: 元数据)
         +------ Shadow RADOS Object 1 (Data: 中间数据)
         +------ Shadow RADOS Object 2 (Data: 中间数据)
         ...
         +------ Tail RADOS Object (Data: 尾部数据)
```
