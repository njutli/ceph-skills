# Note 40 优化建议

## 1. `boost::statechart` 的现代演进
- **原文问题**：原文提到 PG 状态机继承自 `boost::statechart::state_machine`。
- **优化建议**：在现代 Ceph 版本中，部分复杂的 Peering 逻辑已被重构为更扁平化的状态处理函数（如 `PeeringState` 类），以减少 Boost 状态机带来的调试复杂性和性能开销。虽然核心概念依然适用，但源码中可能不再严格遵循 `boost::statechart` 的类继承结构。建议注明"对应早期基于 Boost 状态机的实现"。

## 2. 外部状态的持久化
- **原文问题**：原文未提及外部状态的持久化。
- **优化建议**：补充说明外部状态（`pg_state_t`）不仅用于向 Monitor 汇报，还会被持久化到 `pg_info_t` 中。当 OSD 重启时，它会从 RocksDB 读取上次保存的外部状态，并据此恢复内部状态机的初始位置，加速 Peering 过程。

## 3. `state_set` 与 `state_clear` 的线程安全
- **原文问题**：原文展示了 `state_set` 和 `state_clear` 的调用。
- **优化建议**：指出这些操作是在 PG 的 `OpSequencer` 锁保护下进行的，确保状态变更与 IO 处理的原子性。这避免了在并发场景下出现"状态机显示 Active 但实际仍在 Peering"的竞态条件。

## 4. 常见外部状态组合
- **优化建议**：补充几个常见的外部状态组合及其含义：
  - `active+clean`：健康状态，所有副本同步且 IO 正常。
  - `active+degraded`：主副本在线可读写，但部分副本缺失或正在恢复。
  - `active+remapped`：数据正在迁移到新 OSD，但旧 OSD 仍提供服务。
  - `peering`：PG 正在协商数据一致性，暂时不可服务。
  - `down`：Peering 失败，数据可能丢失或无法恢复。
