# 权重优先级队列 (WPQ) 工作流程解析

## 1. 核心机制
基于权重概率和请求大小过滤（Cost Check）的调度策略。
1.  **选队列**：`rand() % total_prio`。权重越大，被选中的概率越高。
2.  **选请求**：`rand() % max_cost <= threshold`。请求越小（Cost小），被选中的概率越高。

## 2. 流程案例演示
假设场景：**ClientOp (权重 80, 10KB)** vs **Recovery (权重 20, 90KB)**。总权重 100。

### 第一步：掷骰子选队列 (概率选择)
*   **机制**：调度器生成一个 `[0, 99]` 的随机数。
*   **区间划分**：
    *   **[0, 79] (80%)**：落入 ClientOp。
    *   **[80, 99] (20%)**：落入 Recovery。
*   **推演**：假设随机数是 **5** (小于 80)，调度器选中了 **ClientOp**。

### 第二步：看脸色查请求 (Cost 过滤)
*   **机制**：检查被选中队列的队首请求大小。
*   **公式**：`rand(0~99) <= 100 - (req_size * 0.9)`
    *   *注：max_cost 假设为 100。*
*   **推演 ClientOp (10KB)**：
    *   阈值 = `100 - 9 = 91`。
    *   只要随机数小于 91 就放行。通过率 **91%**。
    *   **结果**：**请求顺利出队**。
*   **反例推演 Recovery (90KB)**：
    *   假设第一步摇到了 Recovery（概率 20%）。
    *   阈值 = `100 - (90 * 0.9) = 19`。
    *   通过率仅 **19%**。
    *   **结果**：大概率被拦截，**调度器重置并重新摇奖**。

## 3. WPQ vs Prio 对比
| 特性 | **Prio (旧版)** | **WPQ (新版)** |
| :--- | :--- | :--- |
| **调度方式** | **死板轮询** (小数字优先) | **概率摇奖** (权重决定胜算) |
| **极端情况** | 没令牌就卡死，容易导致死锁 | **永不卡死**，永远有概率被调度 |
| **对大请求** | 无差别对待 (只看令牌) | **天然排斥**，大请求极易被拦截重试 (自动掐尖) |
