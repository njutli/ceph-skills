## 1. 故障恢复核心机制

MDS 故障恢复是保障 CephFS 高可用性的关键，主要依赖 **Journal（日志）** 和 **RADOS** 的持久化能力。由于 MDS 是无状态（或弱状态）的守护进程，数据都在 RADOS 中，因此恢复过程主要是**状态重建**。

### 1.1 为什么故障恢复很复杂？
- **日志庞大与过时**：Replay 的日志量可能很大，且包含过时的中间状态。
- **迁移歧义 (Ambiguity)**：如果 MDS 在子树迁移过程中宕机（如 `EExport`），会导致子树归属权不清，需要 Resolve 阶段解决。
- **实时状态丢失**：MDS 大量依赖实时信息（锁状态、客户端 Capability），这些信息不全部写入日志（成本太高），恢复时需要重新与各节点/客户端协商。
- **客户端无感知**：恢复后的 MDS 必须保证客户端的文件句柄（File Handle）依然有效。

### 1.2 恢复的四个阶段 (State Machine)
基于 `src/mds/MDSRank.cc` 源码，恢复流程严格遵循以下状态机：

#### (1) Replay (日志重放) -> `STATE_REPLAY`
- **动作**：新接管 Rank 的 MDS (Rank B) 读取 Rank A 的 Journal 对象，恢复未刷入底层对象的脏元数据。
- **源码**: `replay_done()`
- **逻辑**：若集群只有一个 MDS，跳过 Resolve 直接 Reconnect；若有其他 MDS，进入 Resolve。

#### (2) Resolve (权威解决) -> `STATE_RESOLVE`
- **动作**：解决多节点分布式事务歧义（如 pending 的 rename、unlink）和迁移中的子树归属权。
- **源码**: `resolve_start()` -> `MDCache::resolve_start()`
- **逻辑**：向其他存活的 MDS 发送 Resolve Map，确认哪些子树的 Authority 属于自己。

#### (3) Reconnect (客户端重连) -> `STATE_RECONNECT`
- **动作**：重新建立与 Client 的 Session。
- **源码**: `server->reconnect_clients()`
- **逻辑**：MDS 向 Client 发送 Reconnect 消息，Client 汇报自己持有的 **Capabilities (Caps)** 和句柄。MDS 据此在 Cache 中重建锁状态。

#### (4) Rejoin (缓存修复) -> `STATE_REJOIN`
- **动作**：同步非权威元数据副本和锁状态。
- **源码**: `rejoin_start()` -> `MDCache::rejoin_send_rejoins()`
- **逻辑**：
  - 恢复中的 MDS 发送 `WeakRejoin`（声明自己恢复了哪些主数据）。
  - 其他活着的 MDS 回复 `StrongRejoin`（告知副本数据和锁）。
  - 最终 Rank B 进入 **`STATE_ACTIVE`**。

## 2. 关键概念解析

### 2.1 Rank (逻辑分片) vs Daemon (守护进程)
- **Rank**: 文件系统的逻辑划分（如 Rank 0, Rank 1...）。
- **Daemon**: 实际运行的后台进程（如 mds.a）。
- **关系**: 一个 Daemon 映射到一个或多个 Rank。

### 2.2 "谁来做新的 Rank A？" (Takeover Logic)
- **Standby 接管 (推荐)**: Monitor 优先将空闲的 Standby MDS 提升为新的 Rank 拥有者，以保持负载均衡。
- **存活节点接管 (Fallback)**: 如果没有 Standby，存活的 MDS（如 Rank B）可能会被要求同时管理 Rank A 的工作量。

## 3. 核心源码追踪

### 3.1 状态机流转示例 (`src/mds/MDSRank.cc`)

```cpp
// 1. 重放完成后的决策 (Line 1954-1963)
void MDSRank::replay_done() {
    // ...
    if (mdsmap->get_num_in_mds() == 1) { 
        request_state(MDSMap::STATE_RECONNECT); // 单节点跳过 Resolve
    } else {
        request_state(MDSMap::STATE_RESOLVE);   // 多节点需确认权威权
    }
}

// 2. Resolve 完成后
void MDSRank::resolve_done() {
    request_state(MDSMap::STATE_RECONNECT);
}

// 3. Reconnect 完成后
void MDSRank::reconnect_done() {
    request_state(MDSMap::STATE_REJOIN);
}

// 4. Rejoin 启动
void MDSRank::rejoin_start() {
    mdcache->rejoin_start(...);
    // ...完成后自动转为 STATE_ACTIVE
}
```

### 3.2 Resolve 阶段的核心操作
- `MDCache::rollback_uncommitted_fragments()`: 回滚失败的目录 Split 操作。
- `calc_recovery_set()`: 确定受影响的 MDS 集合，仅与受影响的节点通讯，减少恢复风暴。

## 4. 实例：Rank B (mds.d) 接管宕机的 Rank A (mds.a)

1. **Monitor 检测**：`mon.a` 没收到 `mds.a` 的 Beacon，标记 Rank A 为 down。
2. **选举替补**：`mon.a` 将 Rank A 指派给 Standby `mds.d`。
3. **Replay**: `mds.d` 挂载 Rank A 的 Journal，加载修改过的元数据（未写回的 Inode/Dentry）。
4. **Resolve**: `mds.d` 告诉 `mds.b`：“我是 Rank A 了，把你那边的 Rank A 缓存（非权威副本）丢弃”。
5. **Reconnect**: `mds.d` 告诉 Client：“我是新的 MDS，重新把你的 Capabilities 给我”。
6. **Rejoin**: `mds.d` 从 `mds.b` 获取必要的元数据副本，正式对外提供服务。
