# Note 14 优化建议

## 1. 术语精确化：Redirect-on-Write vs COW
- **原文问题**：原文将方案二称为"重定向写 (Redirect-on-Write / COW)"。
- **优化建议**：严格来说，**Redirect-on-Write (ROW)** 和 **Copy-On-Write (COW)** 有细微区别。COW 通常指复制旧数据块再修改，而 ROW 指直接将新数据写入新位置并更新指针。BlueStore 的行为更接近 **ROW** 或 **Extent Split/Overlay**。建议统一使用"重定向写 (ROW)"或"覆盖写新 Extent"，避免与快照场景下的 COW 混淆。

## 2. 读取合并机制
- **原文问题**：原文提到"读取时同时加载重叠的多个 Extent，解压并在内存中拼凑"。
- **优化建议**：补充说明 BlueStore 的读取合并是在 `BlueStore::_do_read` 中完成的。它会遍历 `extent_map`，找出覆盖请求逻辑范围的所有物理 Extents，按需解压并拷贝到用户缓冲区。如果重叠 Extent 过多，确实会增加 CPU 开销和读取延迟。

## 3. 后台 GC 的作用
- **原文问题**：原文未提及碎片何时清理。
- **优化建议**：强调 **BlueStore GC 线程** 的作用。它会定期扫描包含多个小 Extent 或大量无效数据的区域，将其合并重写为单个连续 Extent，从而恢复读取性能并释放空间。这是解决 ROW 带来碎片问题的关键机制。

## 4. 压缩算法的影响
- **优化建议**：不同压缩算法（Zlib, LZ4, ZSTD）的解压速度不同，会影响方案一的 RMW 代价和方案二的读取合并代价。LZ4 极快，可能让方案一的代价相对可接受；而高压缩比算法（如 ZSTD）会显著放大 RMW 的延迟，使得方案二成为更优选择。
