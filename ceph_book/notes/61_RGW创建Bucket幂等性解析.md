# RGW 创建 Bucket 流程解析（幂等性）

## 1. 疑问记录

## 2. 分析
这里并不是要真的创建一个新 Bucket 覆盖旧数据，而是处理分布式系统中常见的**幂等性（Idempotency）**问题。

### A. 什么是幂等性？
在 HTTP 协议中，`PUT` 操作（如 `Create Bucket`）必须是幂等的。即：无论客户端发送一次还是多次相同的创建请求，服务器的状态必须一致，且不能破坏现有数据。

### B. 源码逻辑推演
当客户端发送 Create Bucket 请求，且该 Bucket 已经存在时，RGW 会执行以下检查：

1.  **策略比对**: RGW 会读取数据库中现有 Bucket 的配置（`RGWBucketInfo`），并与客户端请求中的参数（主要是存储策略 `placement_rule`）进行比对。
2.  **分支处理**:
    *   **情形一：策略相同 (Conflict)**
        *   含义：客户端请求创建一个已有的 Bucket，且参数一致（通常是因为网络超时重试导致的）。
        *   结果：RGW **不会**重新初始化 Bucket，不会清空数据，也不会创建新的索引对象。**原有数据完好无损**。根据 S3 协议规范，RGW 将返回 **`409 Conflict`** 并附带 `BucketAlreadyOwnedByYou` 错误码，明确告知客户端 Bucket 已存在但操作是安全的。
    *   **情形二：策略不同 (Conflict)**
        *   含义：客户端请求使用的存储策略（例如指向 SSD 池）与现有 Bucket 的策略（例如指向 HDD 池）冲突。
        *   结果：RGW 返回 **409 Conflict**（冲突错误）。不允许覆盖，从而保护了现有数据的路由规则不被破坏。

### C. 结论
图中的逻辑"相同 -> 继续创建/完成"实际上应该理解为：
**"如果 Bucket 存在且策略一致，则视为创建成功（跳过物理创建步骤）；只有当 Bucket 不存在时，才执行真正的物理资源分配。"**
