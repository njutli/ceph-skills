# RGW 对象上传数据拆分与重叠解析 (图 7-11)

## 1. 疑问记录
书中"图 7-11"展示了块大小 2MB、条带 5MB 时上传 9MB 的数据流程。
**问题**:
1.  **切分规律**: 为什么 Object1 存 0~2M，Object2 存 2~7M，Object3 存 7~9M？这是什么规律？
2.  **重复上传**: 为什么 7~8M 这一段数据在"6~8M 上传"和"7~9M 上传"这两个流程步骤中都出现了？是否意味着数据被物理写了两遍？

## 2. 分析

### A. 切分规律：Head + Stripe + Tail
这种切分遵循 RGW 底层对象结构定义的物理规则：

*   **Object 1 (0~2MB) —— Head (头对象)**:
    *   **限制**: `rgw_max_chunk_size` (设为 2MB)。
    *   **原因**: Head 对象不仅要存储数据，还要存储元数据（xattr/omap）。为了防止读取元数据时加载过多物理块（例如读取 1GB 才能看到头部元数据），RGW 强制限制头部对象的大小上限。
    *   **逻辑**: 文件的前 `rgw_max_chunk_size` 数据必然存放在 Head 对象中。
*   **Object 2 (2~7MB) —— Stripe (标准条带对象)**:
    *   **限制**: `stripe_size` (设为 5MB)。
    *   **规则**: 除去 Head 之后的剩余数据，按照标准条带大小进行切分。
    *   **逻辑**: 2MB (Head) + 5MB (Stripe) = 7MB。中间的 2~7MB 数据正好填满这个条带。
*   **Object 3 (7~9MB) —— Tail (尾部对象)**:
    *   **规则**: 剩余不足一个条带大小的数据。
    *   **逻辑**: 9MB - 7MB = 2MB。这最后一段数据单独存放。

> **公式**:
> *   **Head**: 0 ~ `rgw_max_chunk_size`
> *   **Stripe**: `rgw_max_chunk_size` ~ `rgw_max_chunk_size` + `stripe_size`

### B. 重复现象：边界切分逻辑
7~8M 的数据并没有被物理重复存储，而是被 **逻辑拆分 (Split)** 并路由到了不同的对象。

*   **场景还原**:
    内存缓冲区（Buffer）中有一段连续数据 **6~8MB**。RGW 正在处理这段数据写入。
*   **处理过程**:
    1.  **检查边界**: RGW 发现 **7MB** 处是 Object 2 的终点，也是 Object 3 的起点。
    2.  **动作一 (写 Object 2)**: 从 6~8MB 的 Buffer 中切出 **6~7MB**，写入 Object 2。此时 Object 2 填满了。
    3.  **动作二 (写 Object 3)**: Buffer 中还剩余 **7~8MB**。这段数据必须开启新的对象写入流程，分配给 Object 3。
*   **图解**:
    图示为了展示这个路由跳转，将"6~8M"作为源数据的来源，展示了前半截（6~7M）去了 Object2，后半截（7~8M）作为下一轮 I/O 的起点去了 Object3。

**结论**:
数据没有重复。图示展示的是**同一块内存数据**因跨越了**对象物理边界**而被拆分给不同处理逻辑的过程。
