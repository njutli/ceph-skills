# 43. PG同步OSDMap机制详解：为何不能跳跃与分多次同步

本节解释 4.3.3 小节中提到的 PG 同步 OSDMap 的两个关键机制：为什么必须按顺序同步（不能跳跃到最新版本），以及“分多次同步”的具体含义。

## 1. 为什么不能直接同步到最新版本？

PG 的状态机是**基于事件驱动**的。中间的 OSDMap 版本变化（Delta）包含了触发关键行为（如 Peering、Recovery、Backfill）的必要信息。如果直接从 v100 跳跃到 v103，PG 将丢失中间的**状态变迁过程**。

### 详细例子：
假设 PG 1.0 当前处于 OSDMap **v100**，最新为 **v103**。

*   **v100**: ActingSet = `[OSD.1, OSD.2, OSD.3]`。正常。
*   **v101**: **OSD.2 宕机**。
    *   新 ActingSet = `[OSD.1, OSD.3]`。
    *   **关键动作**：PG 发现 OSD.2 丢失，标记 `Degraded`，**触发 Peering**。
*   **v102**: **OSD.2 恢复上线**。
    *   新 ActingSet = `[OSD.1, OSD.2, OSD.3]`。
    *   **关键动作**：PG 发现 OSD.2 回来，标记 `Backfilling`，**开始数据回填**。
*   **v103**: 存储池 Size 从 3 改为 2。
    *   新 ActingSet = `[OSD.1, OSD.2]`。
    *   **关键动作**：PG 发现 OSD.3 被移除，清理数据。

**如果直接跳跃到 v103（错误做法）：**
*   **漏掉故障**：PG 只看到 v100 和 v103 的差异（OSD.3 被移除），完全不知道 OSD.2 曾经宕机过。
*   **数据不一致**：因为没看到 OSD.2 宕机，PG 不会触发 Peering 和 Backfill。OSD.2 上的数据可能已经过期，但 PG 认为它是正常的。
*   **PastIntervals 错误**：无法正确构建历史记录，导致后续无法判断哪些 OSD 拥有权威数据。

**结论**：PG 必须“经历”中间的版本变化，才能正确感知故障、触发修复流程。

## 2. “分多次同步”的含义

如果 OSD 断网很久，重新上线时可能积压了 **10,000** 个新版本。如果 PG 在一个函数调用里处理完所有版本：
*   **CPU 飙升**：计算 10,000 次 ActingSet 变化非常耗时。
*   **阻塞 OSD**：OSD 主线程被卡住，无法处理客户端 IO 或回复心跳。
*   **OSD 被踢出**：Monitor 收不到心跳，会将 OSD 标记为 Down，导致更严重的集群震荡。

**分多次同步策略（Time Slicing）：**
OSD 采用**时间片轮转**的方式，将巨大的工作量切碎：
1.  **第 1 轮**：PG 处理 v100 -> v200（处理 100 个版本）。
2.  **让出 CPU**：处理完后主动返回，OSD 处理心跳和 IO。
3.  **第 2 轮**：PG 继续处理 v200 -> v300。
4.  ...
5.  **完成**：直到追上最新版本。

**总结**：分多次同步是为了**性能保护和防阻塞**，确保 OSD 在追赶进度的同时，依然能响应集群通信。
