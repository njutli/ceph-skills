# 49. GetMissing机制_权威日志与分歧日志的关系解析

## Q: GetMissing阶段中，Missing列表、权威日志（Authoritative Log）、分歧日志（Divergent Logs）的逻辑关系是什么？
## Q: Missing列表里记录了什么？是对象ID，还是具体版本？
## Q: Missing列表的处理流程是怎样的？

### 1. Missing 列表的本质：对象 -> 任务 的映射 (To-Do List)
Missing 列表并非简单的“丢失对象清单”，而是一份**“状态迁移任务单”**。
在 Ceph 源码中，`pg_missing_t`（即 Missing 列表的底层类型）实际上是一个 **Map 结构**（字典/哈希表），而非单纯的列表或队列。
*   **Key**: `hobject_t`（对象 ID）。
*   **Value**: `pg_missing_item`（任务明细），包含以下关键信息：
    *   **`have`**: 对象当前在本地拥有的版本（现状）。
    *   **`need`**: 对象需要恢复到的权威版本（预期状态）。
    *   **`is_divergent`**: 标记是否为分歧对象。若是，则需执行回滚操作（rollback）。
*   **核心结论**：Missing 列表记录的不仅是“缺哪个对象”，而是明确指出了**“针对哪个特定对象，需要执行什么特定操作（拉取或覆盖），以使其达到某个预期状态”**。

### 2. 三个核心概念的关系定义
#### **权威日志 (Authoritative Log)：标准 (Truth)**
*   代表该 PG 当前**唯一正确的数据历史和状态**。Peering 阶段选举出权威日志后，它成为了所有数据恢复的“参照物”或“标准答案”。

#### **分歧日志 (Divergent Logs)：证据 (Evidence)**
*   是在对比本地日志与权威日志过程中，发现的**不匹配（冲突）的历史记录**。
*   **管理方式**：书中明确指出，为了有效解决冲突，**“所有针对同一个对象操作的分歧日志都使用同一个队列进行管理”**。
*   **逻辑含义**：这意味着系统会将**同一个对象**的所有分歧日志条目（可能是多次操作）收集在一起，形成一个逻辑上的**“任务队列”**（或“问题历史清单”）。
*   **作用**：通过这个队列，系统可以按顺序推导该对象的状态演变（例如依据 `prior_version` 判断是回滚还是覆盖），从而准确生成 Missing 列表中的指令。

#### **Missing 列表：指令 (Instruction)**
*   是基于权威日志和分歧日志计算出的**最终恢复指令集**。
*   它不再记录杂乱的历史，而是收敛为具体的任务：对于每个不一致的对象，记录一条唯一的恢复任务。

### 3. 逻辑关系图解
*   **权威日志 vs Missing 列表**：**“买家秀”与“卖家秀”的关系**。
    *   权威日志定义了**目标**。
    *   Missing 列表列出了**差距**（即为了达到目标需要补全的内容）。
*   **分歧日志 vs Missing 列表**：**“体检报告”与“处方”的关系**。
    *   分歧日志记录了**错在哪里**（本地日志中存在的冲突条目）。
    *   Missing 列表记录了**怎么改**（例如：由于分歧存在，必须执行 rollback 将回滚到旧版本）。

### 4. 核心处理流程
这一过程严格遵循以下顺序：
1.  **确定标准 (Peering/GetLog)**：
    *   系统首先选出拥有最完整日志的 OSD，合并生成**权威日志**。此时确立“什么是对的”。
2.  **寻找差异 (Diff)**：
    *   Primary 拿着权威日志与 Peer OSD 的本地日志进行线性比对。
    *   凡是本地日志中多出来的、或版本号不匹配的条目，即被识别为**分歧日志**。此时确立“哪里错了”。
3.  **生成任务 (GetMissing)**：
    *   Primary 根据比对结果构建 **Missing Map**。
    *   **情况 A (普通缺失)**：权威有但本地无，加入 Missing（任务：Fetch/Pull）。
    *   **情况 B (分歧)**：本地有但版本错（有分歧日志），加入 Missing 并标记 `is_divergent`（任务：Rollback/Overwrite）。

### 5. 源码场景案例详解
以下结合源码逻辑 `PGLog::proc_replica_log` 展示两种典型场景：

#### 场景一：权威日志属于 Primary (Primary is Truthful)
**背景**：Primary 的日志是最新且正确的，Replica 曾短暂脑裂或有未确认的写入。
*   **日志状态**：
    *   **Primary (权威)**：`Object A (v10)` -> `Object B (v11)`
    *   **Replica (本地)**：`Object A (v10)` -> `Object B (v13')`
*   **流程分析**：
    1.  **识别分歧**：Primary 对比 Replica 日志，发现 `ver 10` 之后 Replica 存在独有日志 `v13'`。系统判定 `v13'` 为**分歧日志**。
    2.  **队列管理**：系统将针对 `Object B` 的分歧日志归入同一个队列 `split[Object B]`。
    3.  **Missing 生成**：
        *   Primary 发现 Replica 的 `v13'` 是无效的（未获得最终确认），需要回退。
        *   **结果**：在 **Replica 的 Missing 列表**中添加指令：`Object B` -> Need `v11`，Have `v13'` (is_divergent)。
*   **关于 `v13'` 的丢失**：
    *   `v13'` 代表了用户的一次写操作。但由于它未同步到权威日志（最终一致性），因此被视为脏数据。在执行 Recovery 时，Primary 会强制 Replica **丢弃 `v13'`**（回滚），并覆盖以权威的 `v11`。这次写入对于用户来讲最终是**丢失**的。

#### 场景二：权威日志不在 Primary (Primary is Stale/Divergent)
**背景**：Peering 完成后发现 Primary 落后或存在错误版本（"Fake Primary" 场景）。这通常由 OSD 切换或故障导致。
*   **日志状态**：
    *   **Replica (权威)**：曾短暂主导并成功写入，包含 `Object A (v10)` -> `Object B (v15)`
    *   **Primary (本地)**：由于故障未同步成功，包含 `Object A (v10)` -> `Object B (v15')` (脏数据)
*   **流程分析**：
    1.  **构建权威日志**：Peering 机制识别出 Replica 拥有更完整的日志，将其合并为权威权威。
    2.  **自我诊断**：Primary 拿着新生成的权威日志与**自己**的本地日志比对。
    3.  **识别分歧**：发现自己在 `ver 10` 之后多出了 `v15'`，这就是**分歧日志**。
    4.  **Missing 生成 (Self-Recovery)**：
        *   **结果**：Primary 会在**自己的 Missing 列表**中添加一条针对自身的修复指令：`Object B` -> Need `v15` (去 Replica 拉取正确数据)，Have `v15'` (标记自己的旧数据为分歧待清洗)。

### 6. 分歧日志处理中的五种情形解析 (Missing 生成规则)
书中指出，在处理针对同一个对象的“分歧日志队列”时，会归纳为五种处理情形。这些情形决定了该对象是否需要进入 **Missing 列表**，还是需要直接执行特定的存储操作。

#### (1) “对象之前不存在” (情形 2)
这是五种情形中最为特殊的一种，直接涉及到对象的**物理删除**，且通常**不会**生成 Missing 条目。
*   **判定标准**：该对象的分歧日志队列起始版本号 `prior_version` 为 **0**，或者最老的日志操作类型为 `CLONE`。
*   **物理含义**：这意味着该对象完全是由分歧期间的操作“凭空创造”的（即创建操作发生在脑裂期间）。**权威日志中根本不存在该对象。**
*   **执行动作**：**直接物理删除当前 PG 实例（Replica 或 Primary）上的该对象**。
*   **为什么不需要 Missing**：
    *   Missing 列表的目的是“找回丢失的权威数据”。
    *   既然权威日志里没有这个对象，目标状态就是“无”。因此，只要删除掉本地的“幽灵对象”，该实例的状态就瞬间与权威一致了，无需拉取任何数据。
*   **场景示例**：
    *   OSD.2 脑裂期间创建了 `Object A` 并写入 1MB 数据。
    *   恢复 Peering 后，Primary 发现 `Object A` 在权威日志中不存在（属于分歧）。
    *   **结果**：OSD.2 根据规则 2 直接删除磁盘上的 `Object A`，修复完成。

#### (2) “对象当前位于 Missing 列表之中” (情形 3)
这是针对**“连环故障”或“连续掉电”**场景的特殊处理，通常用于**移除误报的修复任务**。
*   **场景背景**：系统在上一轮掉电时发现了该对象的问题，将其放入了 Missing 列表（待修复名单），但还没开始修复就又发生了掉电。
*   **流程分析**：
    1.  **状态继承**：再次恢复时，对象仍标记在 Missing 列表中，且有一条待处理的**分歧日志**（版本号设为 `v11`）。
    2.  **版本比对 (`have` vs `prior_version`)**：
        *   系统检查磁盘上对象的真实状态（`have`）。
        *   如果 `have` 等于分歧日志发生前的版本（`prior_version`，如 `v10`）。
    3.  **判定逻辑**：这说明之前的分歧操作（`v11`）**根本没有成功写入物理介质**，或者说对象依然完好如初地停在旧版本。
*   **执行动作**：**直接将对象从 Missing 列表中移除**。
    *   因为对象本身是准确的 `v10`，分歧日志只是个无效的“幻影”，不需要任何回滚或拉取操作。

#### (3) “对象不在 missing 列表之中同时所有分歧日志都可以回滚” (情形 4)
这是**“本地自我修复”**的最优解，不需要产生跨节点的网络 IO。
*   **场景示例**：
    *   **状态**：`Object A` 存在于本地磁盘（当前版本 `v12`），且不在 Missing 列表中（未被标记为丢失）。
    *   **分歧**：发现本地存在两条分歧日志：`v12` 和 `v11`。
    *   **判断**：系统检查回滚界限（`can_rollback_to`），发现 `v11` 和 `v12` 都在可回滚范围内（未被清理）。
    *   **动作**：按照从新到老（`v12` -> `v11`）的顺序**依次执行回滚操作（Undo）**。数据直接在本地变回 `v10` 的状态。
*   **结果**：本地数据修正完毕，**无需**生成 Missing 条目，也不需要从其他 OSD 拉取数据。

*   **核心解析：脑裂与权威判定**
    *   **什么是脑裂**：指集群因网络分区变成多个孤岛，导致多个 OSD 同时认为自己是 Primary 并对外提供写入服务，从而产生了数据版本的分叉。
    *   **为什么拥有 v12 的 OSD 不是权威？**：在 Ceph 中，数据一致性判断的核心不是单纯的版本顺序号（Version），而是 **Interval 的合法性**（Epoch/Map）。
        *   如果 OSD.1 产生 `v11`、`v12` 的操作是在它**未被集群正式承认的 Interval**（比如它以为自己在线，但系统已经切换了 Primary）发生的，那么它的数据就是**非法的“脑裂写入”**。
        *   相对的，即使 OSD.2 只有旧的 `v10`，只要它的日志是在**合法的 Primary 任期结束**时记录的，它就是权威基线。
        *   **结论**：OSD.1 必须通过**情形 4** 的回滚操作，撤销非法写入，退回到合法的 `v10` 状态。

#### (4) “对象不在 missing 列表之中并且至少存在一条分歧日志不可回滚” (情形 5)
这种情况可以理解为**“无法撤销的脏数据，只能彻底销毁重来”**。
*   **判定标准**：对象在本地存在（状态完好），但在处理分歧日志时，发现**回滚界限（can_rollback_to）**低于分歧日志需要回滚的版本，或者**相关的回滚日志/上下文已被清理**。
*   **场景示例**：
    *   OSD.1 持有脏对象 `Object A` (`v12`)，但无法执行 Undo 操作变回合法的 `v10`（因为日志老化或丢失）。
    *   系统判定：既然无法在本地将脏数据“洗白”成旧版本，就必须清除它。
*   **执行动作**：
    1.  **物理删除**：**直接删除磁盘上的 `Object A` (`v12`)**。因为它是错的，且改不回来。
    2.  **加入 Missing 列表**：
        *   **Have = 0**：标识本地现在没有该对象了。
        *   **Need = prior_version**（例如 `v10`）：设定目标状态为分歧发生前的那个安全版本。
    3.  **标记**：标记该条目需要后续进行 **Refetch**（重新拉取）。
*   **结果**：OSD.1 将自己变成一个“一无所有”的状态，然后在后续的 Recovery 阶段，它会发现自己缺 `v10`，于是向权威节点请求拉取一份完整的数据副本。

#### (5) “本地存在比分歧日志更新的日志” (情形 1)
这是五种情形中的第一种，通常发生在**“假分歧”**或**“覆盖写入”**的场景。
*   **判定标准**：在检查分歧日志队列时，系统发现本地日志中（或已合并的权威日志中）存在一条**版本号更高**的记录。
*   **场景示例**：
    *   本地有一条分歧日志显示对 `Object A` 进行了非法修改（`v11`）。
    *   但是，当前日志头部显示该对象已经到了 `v20`（且该版本是权威的）。
    *   这意味着，那个非法的 `v11` 早就被后续的合法操作覆盖了。
*   **执行动作**：
    *   既然最新的版本 `v20` 已经涵盖了之前的状态，那些旧的分歧日志（`v11`）就不再重要。
    *   系统通常会**清理**这些无关的分歧日志条目。
    *   如果本地对象当前状态与 `v20` 一致，则**直接删除**多余的中间状态记录，通常**不需要**生成 Missing 条目（除非对象已被删除）。

### 总结
**先有权威日志（标准），再有分歧日志（差异诊断），最后生成 Missing 列表（治疗方案）。**
**无论是主 OSD 还是从 OSD，任何与权威日志不一致的“分歧日志”都会被无情抛弃，系统将通过 Missing 列表中的指令或直接删除操作（针对凭空产生的对象），将所有副本强制拉齐到权威状态。**
