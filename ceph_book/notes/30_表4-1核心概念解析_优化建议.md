# Note 30 优化建议

## 1. `acting set` 与 `up set` 的排序
- **原文问题**：原文提到"第一位必须是 Primary OSD，后续位置由 CRUSH 算法决定"。
- **优化建议**：补充说明 Primary 的选择不仅依赖 CRUSH 顺序，还受 `primary_affinity` 和 `primary-recovery` 等参数影响。此外，在 EC 场景下，Primary 通常承担编码/解码计算压力，因此有时会将 Primary 固定在计算能力更强的节点上。

## 2. `pg_temp` 的自动触发
- **原文问题**：原文提到 `pg_temp` 可由 Monitor 自动触发或管理员手动执行。
- **优化建议**：明确指出 `pg_temp` 的自动触发通常发生在 **`mon_osd_down_out_interval`** 超时后，或者当 Monitor 检测到 PG 处于 `down` 状态且存在 `pg_temp` 候选项时。现代 Ceph 中，`pg_upmap` 和 `pg_upmap_items` 已经逐渐取代了传统的 `pg_temp`，用于更精细的手动负载均衡。

## 3. `Interval` 与 `past_intervals`
- **原文问题**：原文解释了 Interval 的概念。
- **优化建议**：补充说明 `past_intervals` 是 PG 元数据（`pg_info_t`）的重要组成部分。它记录了历史上所有 Interval 的 Acting Set 成员。在 Peering 时，Primary 使用 `past_intervals` 来确定哪些 OSD 可能持有旧数据，从而精准定位恢复源，避免全集群扫描。

## 4. `Stray` 对象的现代处理
- **原文问题**：原文详细描述了 Stray 的发现与清理。
- **优化建议**：在现代 Ceph 中，Stray 对象的清理通常由 **`PG::recover_strays`** 函数处理。如果 Stray 对象属于当前 PG 但版本过旧，它会被直接删除；如果属于其他 PG（例如 PG 分裂/合并后残留），它会被重定向到正确的 PG 或放入 `lost+found` 目录供管理员审查。

## 5. `Watch/Notify` 的持久化
- **原文问题**：原文提到 Watch 连接失效后机制自然失效。
- **优化建议**：补充说明 Ceph 支持 **持久化 Watch (Persistent Watch)**。即使 OSD 重启，Watch 注册信息也会保存在 BlueStore 的元数据中，重启后 OSD 会重新建立与客户端的连接，确保分布式锁不丢失。
