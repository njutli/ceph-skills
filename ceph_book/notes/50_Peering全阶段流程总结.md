# 深度解析: Peering全阶段流程总结（1-5阶段）
> [[Notes 详解]]

本节总结 4.3.3 小节 Peering 的全貌。Peering 并非仅到 `GetLog` 为止，它包含完整的“发现真理”到“达成共识”再到“最终激活”的五个阶段。只有当 PG 进入 **Active** 状态，Peering 才宣告完成。

Peering 的核心目标是：在数据同步开始之前，通过交换元数据（日志），选举出唯一的**权威日志（Authoritative Log）**，并为后续的数据修复制定指令。

### 流程全景概览

*   **第 1 阶段：确定历史范围 (past_intervals)**
    *   **核心动作**：OSD 更新 Map 产生 Interval。
    *   **目的**：锁定过去可能发生写操作的“动荡时间段”。
    *   **关键指标**：`maybe_went_rw` 和 `up_thru`。

*   **第 2 阶段：锁定嫌疑人 (GetInfo)**
    *   **核心动作**：构建 **PriorSet** 并发送 **Query 消息**拉取 **Info**。
    *   **目的**：找到所有可能持有“关键证据（日志）”的存活 OSD，获取其概要信息（如 `last_update`）。

*   **第 3 阶段：确立真理 (GetLog)**
    *   **核心动作**：选举权威日志 + 处理本地分歧。
    *   **目的**：确定“谁是最新的、最全的（真理）”，并清洗本地的“脏数据/非法写入”（处理 Divergent Logs）。

*   **第 4 阶段：制定任务 (GetMissing)**
    *   **核心动作**：比对 Peer 日志，生成 **Missing List**。
    *   **目的**：将 Peer 的现状与真理之间的差距，转化为具体指令（需要回滚、需要拉取、还是直接删除）。
    *   **关键逻辑**：解决分歧日志的 5 种情形。

*   **第 5 阶段：持久化与激活 (Activate)**
    *   **核心动作**：落盘（更新 `last_epoch_started`）+ 通知 Peer 激活（变为 `ReplicaActive`）。
    *   **目的**：正式对外服务（PG 状态变为 Active），并构建 `MissingLoc` 准备进入后台 Recovery/Backfill。

---

### 详尽示例：从脑裂到达成共识

假设存储池副本数为 3，**Up Set = [A, B, C]**。当前 PG 初始 Version = `100'10`。

#### 场景演进
1.  **Epoch 101（网络分区）**：A 和 B 与 C 断开。C 以为自己是 Primary，接受了写请求，将 `obj1` 更新为 `101'11`（非法写入）。
2.  **Epoch 102（C 掉电）**：C 断电宕机，OSDMap 最终标记 C 为 Down。
3.  **Epoch 103（A/B 恢复）**：A 和 B 重新上线并发现 Map 变更，触发 **Peering**。

#### Peering 各阶段表现

*   **1. past_intervals（寻找历史）**：
    A 收到 Epoch 103 Map，计算过去时间线。发现 `Interval 101` 中 C 曾作为 Primary，且 `maybe_went_rw = true`。
    > **结论**：A 知道在 Epoch 101 期间，“可能写过数据，需要调查 C 或 B”。

*   **2. GetInfo（收集证据）**：
    A 构建 **PriorSet** [A, B, C]。发送 **Query** 消息：
    *   A: 返回 `100'10`
    *   B: 返回 `100'10`
    *   C: 无响应（已 Down）
    > **结论**：A 获取了所有能联系到的 OSD 的概要信息，锁定 A 和 B。

*   **3. GetLog（确立真理）**：
    A 选举 A/B 的日志为**权威日志**（Version `100'10`）。
    > **结论**：真理确立为 `100'10`。A 自身如果是 `100'10` 则无需处理；如果有旧的脏数据则会被清洗。

*   **4. GetMissing（处理非法数据）**：
    *注：假设 C 后来也重启了，试图重新加入。*
    C 报告它有 `obj1: 101'11`。A 对比权威日志 `100'10`，发现 `101'11` 是**分歧日志（Divergent Log）**。
    *   **操作**：A 判定该写入无效，将 C 上的 `obj1` 标记为 **情形 4（可回滚）** 或 **情形 5（不可回滚）**。
    > **结论**：C 的任务变为“销毁 `obj1` 并恢复到 `100'10` 版本”。

*   **5. Activate（达成共识）**：
    *   A 将 `last_epoch_started` 写盘。
    *   A 通知 B：“你已激活（ReplicaActive）”。
    *   **结果**：PG 进入 **Active** 状态。后台 **Recovery** 模块开始工作，去 C 节点执行回滚任务。
