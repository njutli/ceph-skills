# 56_RADOS 快照底层机制解析

## 1. 核心概念：元数据克隆 vs 物理拷贝

书中提到的创建快照后的“底层克隆操作生成 clone 对象”，**绝不是**物理数据的瞬间拷贝。Ceph 快照之所以能“瞬时完成”，核心在于它是基于**元数据的指针共享**。

### 克隆瞬间发生了什么？
*   **逻辑视图**：生成的 clone 对象看起来拥有完整的旧数据（所谓的“全对象克隆”）。
*   **物理实现**：底层（如 BlueStore）通过 `extent_map.dup` 操作，将 clone 对象指向了 head 对象当前占用的物理块（Blob）。
    *   此时，clone 和 head **共享**同一份物理存储。

## 2. 写入 Head 对象时的数据流向 (COW)

当快照创建后，客户端向 Head 对象写入新数据（如正文中的 $[512\mathrm{K} \sim 1\mathrm{M}]$ 区间），底层存储引擎的机制如下：

1.  **分配新块**：系统不会去覆写旧数据，而是分配一块全新的物理磁盘空间（新 Blob）来存放这 512KB 的新数据。
2.  **更新 Head**：Head 对象的元数据映射表被修改，将该区间的指针指向**新块**。
3.  **保护 Clone**：由于 Clone 对象紧紧抓着**旧块**的引用，旧数据被锁定保护，绝不会被覆盖。

## 3. 为什么快照读能读到旧数据？

写入操作完成后，底层的数据分裂成了两部分视图：

| 对象 | 区间状态 | 数据来源 |
| :--- | :--- | :--- |
| **Clone (快照)** | 依然指向 **旧块** | 读到 **旧数据** (完美保留) |
| **Head (最新)** | 指向 **新块** | 读到 **新数据** |

### 总结 `clone_overlap`
*   `clone_overlap` 记录的是 **Head 和 Clone 目前还共享同一个物理块的区间**。
*   一旦 Head 的某个区间被写入，它就去向了“新块”，该区间便不再重叠（Overlap），这也解释了为何写入操作会导致重叠区间被减去。
