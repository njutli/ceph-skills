## 二、 目录分片 (Directory Fragmentation)

### 2.1 背景与核心概念

**书中原文：**
> *"超大目录的预加载问题……如果每个目录的 Dentry 和 Inodes 只写入到一个对象，在大型目录结构中预读取整个目录的成本太高。"*

**核心痛点：**
1.  **对象大小限制**：MDS 的元数据默认存储在大小不超过 **4MB** 的 RADOS 对象中。
2.  **性能灾难**：若一个目录包含十万个文件，不拆分则会导致 `ls` 等命令因等待巨大对象加载而卡死。
3.  **负载无法分担**：单个目录无法跨越多个 MDS 节点进行管理。

**解决方案：**
通过 **FragTree (分片树)** 机制，将一个逻辑目录拆解为多个 **Fragment (片段)**，每个片段作为一个独立的 RADOS 对象存储。

### 2.2 核心数据结构与源码

**1. `frag_t` (分片标识)**
定义于 `src/include/ceph_frag.h`。
*   **原理**：32 位编码，高 8 位为 `bits` (深度)，低 24 位为 `value` (前缀匹配)。
*   **逻辑**：类似 IP 路由表的掩码匹配。

```cpp
// 判断 hash 值 v 是否在 frag f 范围内
static inline int ceph_frag_contains_value(__u32 f, __u32 v) {
    return (v & ceph_frag_mask(f)) == ceph_frag_value(f);
}
```

**2. `fragtree_t` (分片树)**
定义于 `src/include/frag.h`。
*   **`_splits` Map**：记录目录分裂的节点和深度。
*   **同化优化**：子节点分裂模式一致时可合并，保持树结构紧凑。

### 2.3 案例推演：`/data/` 目录的分裂

假设 `/data/` 目录从 0 增长到 50 万个文件。

*   **阶段 1：初始状态 (未分裂)**
    *   `frag=0x000000/0`，对应对象名为 `200.00000000` (Inode 为 200)。
*   **阶段 2：触发分裂 (超过阈值)**
    *   `src/mds/CDir.cc:should_split()` 判断目录下项超过阈值（如 1 万）。
*   **阶段 3：2-bit 分裂 (1 变 4)**
    *   原 `frag=0x000000/0` 分裂为 4 个子片段：
        *   `00*` -> `0x000000/2` -> 对象 `200.00000000`
        *   `01*` -> `0x400000/2` -> 对象 `200.40000000`
        *   `10*` -> `0x800000/2` -> 对象 `200.80000000`
        *   `11*` -> `0xc00000/2` -> 对象 `200.c00000000`

**文件名定位流程：**
1.  计算文件名 Hash (`hash_dentry_name`).
2.  查 `fragtree_t` 得到对应的 `frag`.
3.  通过 `CInode->dirfrags` 找到对应 `CDir` 对象。

### 2.4 目录分片与负载均衡的关联

目录分片是实现 MDS 负载均衡的**物理基础**。
*   **独立存储**：每个 Fragment 是独立的 RADOS 对象，解决了存储和 IO 瓶颈。
*   **最小调度单元**：MDS 不能只迁移目录的一半，但可以迁移一个 Fragment。
    *   *源码体现*：`CDir` 对象的 `dir_auth` 属性，允许不同的 Fragment 归属不同的 MDS，从而实现"子树迁移"（见下文）。

## 三、 子树分区 (Subtree Partition)

### 3.1 核心概念

**书中原文：**
> *"由于子树元数据被定义在组目录 Fragment 中，所以可以通过在 MDS 之间迁移 Fragment 来实现负载均衡..."*

**定义：**
子树分区是指在**逻辑层面**，将文件系统目录树的不同分支（或单个 Fragment）分配给不同的 MDS 节点管理，同时保持文件系统命名空间的统一性。

### 3.2 源码核心数据结构

子树分区的核心在于**权限标记 (Authority)** 和**边界映射 (Bounds)**。

**1. `dir_auth` (目录权威)**
定义于 `src/mds/CDir.h`。
*   **作用**：标识**谁拥有该目录（或分片）的读写权限**。
*   **特殊值**：
    *   `AUTH_PARENT (-1, -1)`：继承父级权限（默认，未分片状态）。
    *   `(mds_rank, -1)`：指定特定 MDS 拥有独占权威。

**判定逻辑**：
*   `CDir::is_subtree_root()`：当 `dir_auth != AUTH_PARENT` 时，该 CDir 就成为了一个子树的根（子树边界）。

**2. `subtrees` Map (子树映射)**
定义于 `src/mds/MDCache.h`。
*   **结构**：`map<CDir*, set<CDir*>>`
*   **逻辑**：MDS 使用此结构记录管辖范围内的子树层级。
    *   Key: 父目录 CDir
    *   Value: 下属的子树根 CDir 集合

**3. `adjust_subtree_auth()`**
定义于 `src/mds/MDCache.cc`。
*   **作用**：这是负载均衡的核心执行函数。Balancer 通过修改 `dir_auth` 来实现子树在不同 MDS 间的"搬家"。

### 3.3 案例推演：`/data/` 目录的子树迁移

假设集群中有 **MDS.0** (管理根目录 `/`) 和 **MDS.1**。Balancer 决定将热点目录 `/data` 从 MDS.0 迁移给 MDS.1。

**1. 迁移前：**
*   所有目录的 `dir_auth` 均为 `AUTH_PARENT`。MDS.0 拥有绝对控制权。

**2. 执行迁移 (Balancer 发起)：**
*   **在 MDS.1 上 (新权威)**：
    *   加载 `/data` 的元数据。
    *   设置 `/data` 的 `dir_auth = (1, -1)`，标记为 **Local Subtree**。
*   **在 MDS.0 上 (旧权威 -> 边界)**：
    *   发现 `/data` 的权限变为 1，MDS.0 将其变为**代理点/边界**。
    *   更新 `subtrees` Map：记录 `/` 下面挂了一个属于 MDS.1 的边界 `/data`。

**3. 关键机制：祖先元数据复制 (Ancestor Replica)**
*   为了让 MDS.1 能够解析 `/data/file.txt` 并确认权限，MDS.1 必须知道自己是挂载在 `/` 下面的。
*   **操作**：MDS.0 将 `/` (根目录) 的元数据**副本**同步到 MDS.1 的缓存中。
*   **结果**：MDS.1 缓存中形成了 ` [虚线框] / -> [实线框] /data ` 的完整路径树。

**4. 客户端访问流程 (Lookup)：**
1.  客户端请求 `ls /data` -> 随机到达 **MDS.0**。
2.  MDS.0 检查 `/data` 的 `dir_auth`，发现是 `1`。
3.  MDS.0 判定自身无权处理，将请求**转发**给 **MDS.1** (或引导客户端直连 MDS.1)。
4.  **MDS.1** 处理请求，访问本地权威的 `/data` 子树。

### 3.4 子树分区的效果总结

通过子树分区，Ceph MDS 实现了：
1.  **分布式权威**：不同的子树归属不同的 MDS，消除了单一元数据服务器的性能瓶颈。
2.  **单一命名空间 (Single Namespace)**：客户端无需关心底层结构，看到的依然是统一的文件系统树。
3.  **动态调整**：Balancer 通过监控热度，随时移动子树边界，实现热度的动态平衡。

## 四、 元数据复制 (Metadata Replication)

### 4.1 核心概念

**定义：**
子树分区解决了"**谁拥有元数据 (Authority)**"的问题，而元数据复制解决的是"**谁可以快速读取元数据 (Read Access)**"和"**如何解析跨节点路径 (Path Resolution)**"的问题。

**核心机制：**
MDS 缓存中的每个对象 (`CDir`/`CInode`) 都会通过状态位和映射表记录自己在这个分布式网络中的身份：
*   **Auth (权威副本)**：拥有唯一读写权限。
*   **Replica (非权威副本)**：用于读取、路径解析，可有多个。

### 4.2 源码核心数据结构

**1. `CDir::state`**
*   `STATE_AUTH`：表示该 MDS 是此对象的权威节点。
*   缺失此标志但在 Cache 中：表示该 MDS 持有的是一个**副本 (Replica)**。

**2. `CDir::replica_map`**
*   **定义**：`map<mds_rank_t, replica_info_t>`
*   **位置**：存在于**权威 MDS**的缓存对象中。
*   **作用**：**权威节点**用来记录"谁手里有我的副本"。
    *   *应用场景*：当权威节点需要删除或修改元数据时，必须遍历 `replica_map`，通知所有持有副本的节点失效旧数据（Revoke/Cap Message），保证一致性。

### 4.3 案例推演：跨节点查找与 "Bound" 机制

**场景设置**：
*   **MDS-0**：管辖根目录 `/` (Auth)。
*   **MDS-1**：通过子树分区，管辖子目录 `/data` (Auth)。
*   **请求**：客户端向 MDS-1 发送请求 `ls /data/file.txt`。

#### 4.3.1 触发复制 (Ancestor Replica)
为了让 MDS-1 能够确认 `/data` 是合法挂在 `/` 下面（以及检查权限链），MDS-1 必须拥有根目录 `/` 的信息。
*   **动作**：MDS-0 将 `/` 的元数据作为 **副本** 发送给 MDS-1。
*   **状态**：MDS-1 缓存中有了 `/` (Replica) 和 `/data` (Auth)。

#### 4.3.2 逻辑冲突 (为什么需要 Bound？)
在 MDS-1 看来，它缓存了 `/` 的结构。通常情况下，`/` 下面的 `data` 目录应该归属于 `/` 的权威（即 MDS-0）。
*   **如果不引入 Bound 机制**：
    *   当 MDS-1 解析 `/data/...` 时，它会查 `/` 的副本，发现 `/data` 属于 MDS-0。
    *   MDS-1 会将请求**转发给 MDS-0**。
    *   MDS-0 收到后会拒绝/踢皮球："`/data` 已经切分给你 MDS-1 了！"
    *   **结果**：死锁或请求循环。

#### 4.3.3 解决方案：Subtree Bound
为了解决上述冲突，Ceph 要求副本元数据必须记录**边界 (Bounds)** 信息。

*   **MDS-1 缓存中的 `/` 副本结构**：
    ```text
    CDir(/):
      - State: Replica (Auth 是 MDS-0)
      - Bounds: { "/data" }  <-- 关键!
    ```
*   **解析逻辑**：
    1.  MDS-1 查找 `/data`。
    2.  发现自己持有 `/` 的副本。
    3.  检查 `/` 的 `Bounds` 列表：**命中！**
    4.  **决策**：系统意识到 `/data` 虽然是 `/` 的子目录，但由于它被切分并在本地拥有 Auth，**截断转发链**。
    5.  **结果**：MDS-1 直接在本地处理请求，不再询问 MDS-0。

### 4.4 书中提到的 4 个约束 (源码映射)

| 书中约束 | 核心含义 | 源码对应机制 |
| :--- | :--- | :--- |
| **1. 缓存元数据与根关联** | MDS 必须能看到根节点才能解析路径 | **Ancestor Replica** (向上复制直到根) |
| **2. 保存父类同一级的 Bound** | 副本必须知道哪里切分出了本地子树 | **Subtree Bound List** |
| **3. 副本知权威位置** | 副本节点知道去哪里请求写操作 | **`dir_auth` 标记** |
| **4. 权威知副本信息** | 权威节点知道谁有副本以便发失效通知 | **`replica_map`** |

### 4.5 总结

*   **目录分片**：解决大目录的 IO 问题（拆箱装）。
*   **子树分区**：解决 MDS 的计算扩展问题（分地盘）。
*   **元数据复制**：解决跨节点的查找效率和路径合法性问题（发地图）。
    *   其中 **Bound** 机制是连接复制与分区的粘合剂，防止 MDS 在面对"拥有副本的目录"时迷失在管辖权中。

## 五、 子树迁移 (Subtree Migration)

### 5.1 核心概念

**书中原文** 提供了两种迁移方案：
1.  **落盘方案**：将子树元数据存储到 RADOS 后端，然后在目的 MDS 中重新读取加载。
2.  **动态迁移方案（Ceph 采用）**：直接在内存中将源 MDS 的缓存数据发送给目的 MDS。

**定义：**
子树迁移是指在系统运行期间，不经过磁盘，将元数据从一个 MDS 的内存缓存直接传输到另一个 MDS 的内存缓存，以平衡负载。

### 5.2 源码核心结构

迁移逻辑集中在 `src/mds/Migrator.h` 和 `src/mds/Migrator.cc` 中。

**1. `Migrator` 类**
*   **职责**：全权负责 Export 和 Import 流程。

**2. 关键日志事件 `EExport`**
定义于 `src/mds/events/EExport.h`。
*   **作用**：记录迁移的中间状态。如果源 MDS 在迁移过程中宕机，新的 MDS 重启后通过 Replays `EExport` 日志，能够恢复迁移状态，防止数据丢失。

### 5.3 案例推演：`/data/` 目录的完整动态迁移

**场景：** 集群有 **MDS-0** 和 **MDS-1**。MDS-0 正权威管理 `/data`，Balancer 决定将其迁移给 MDS-1。

#### 阶段 1：准备与冻结 (Source MDS-0)
1.  **发起迁移**：`Migrator::export_dir()` 被调用。
2.  **锁定目录**：目录状态被设为冻结。
    *   `dir_auth` 变为 `(0, 1)` (表示正在从 0 迁移到 1，状态具有二义性)。
    *   `STATE_FREEZING`：阻止新请求进入，等待现有请求完成。
3.  **日志记录起点**：MDS-0 记录迁移开始的事件到日志。

#### 阶段 2：序列化与传输 (Source MDS-0 -> Target MDS-1)
1.  **打包数据**：MDS-0 将 `/data` 目录下的所有 **Dentry** 列表打包到 Bufferlist 中。
    *   注意：不仅打包 `/data` 本身，还会打包它对应的 **Ancestor Replica**（根目录 `/` 的副本元数据），以保证 MDS-1 能解析完整路径。
2.  **发送 `MExportDir`**：MDS-0 通过集群内部网络向 MDS-1 发送包含打包数据的消息。

#### 阶段 3：接收与构建 (Target MDS-1)
1.  **接收消息**：MDS-1 收到 `MExportDir`。
2.  **构建 Import**：
    *   在 MDS-1 内存中创建 `CDir` 对象。
    *   填充 Dentry 列表。
    *   构建 Bound 关系。
3.  **确认收到**：MDS-1 回复 `MExportDirAck` 给 MDS-0。

#### 阶段 4：日志提交 (Source MDS-0)
1.  **收到 Ack**：MDS-0 确认 MDS-1 已收到数据。
2.  **写入 `EExport`**：**关键步骤**。MDS-0 将此次迁移的元数据变更写入 RADOS 日志 (Journal)。
    *   *安全屏障*：只有落盘确认，MDS-0 才会认为迁移真正成功。

#### 阶段 5：完成与清理
1.  **发送 Finish**：MDS-0 向日志落盘确认后，向 MDS-1 发送 **`MExportDirFinish`**。
2.  **MDS-1 确权**：
    *   收到 Finish 后，MDS-1 将 `/data` 的 `dir_auth` 修改为 **`(1, -1)`**。
    *   此时 MDS-1 正式成为权威，开始处理客户端请求。

### 5.4 为什么需要 `EExport` 日志？

假设 MDS-0 在 **阶段 3 (MDS-1 收到数据)** 之后，**阶段 4 (MDS-0 收到 Ack 但尚未写日志)** 崩溃了：
*   **结果**：MDS-1 有数据，但不知道自己是权威；或者 MDS-1 以为自己权威但 MDS-0 的旧日志没更新。
*   **恢复逻辑**：
    *   重启后的 MDS (或者新的 MDS) 会 Replay 日志。
    *   如果没有 `EExport` 日志，系统会认为 `/data` 还在 MDS-0。
    *   有了 `EExport` 记录，系统就知道迁移发生过，从而恢复状态，避免"脑裂"（即两个 MDS 都认为自己拥有 `/data`）。

## 六、 整体架构总结

**目录分片**、**子树分区**、**元数据复制**与**子树迁移**构成了 MDS 实现高扩展性的完整闭环：

1.  **物理层 (Fragmentation)**：**拆解**。将大目录切碎成多个物理对象，打破 4MB 限制，便于流动。
2.  **管理层 (Partition)**：**划分**。通过 `dir_auth` 权限标记，将碎片（或目录分支）分配给不同 MDS。
3.  **协调层 (Replication)**：**同步**。利用 Ancestor Replica 建立全路径视图，利用 Bounds 解决路由冲突。
4.  **调度层 (Migration)**：**搬动**。利用 Migrator 和日志系统，在内存中安全、动态地搬运元数据，实现负载均衡。
