# Note 64 优化建议

## 1. `Resolve` 阶段的精确作用
- **原文问题**：原文提到 Resolve 解决多节点分布式事务歧义。
- **优化建议**：补充说明 `Resolve` 阶段的核心是 **`MDCache::resolve_start`** 和 **`MDCache::resolve_ack`** 消息交换。它不仅解决子树迁移歧义，还处理 **未完成的 Rename/Link/Unlink 操作**。这些操作可能涉及多个 MDS，如果在事务中间宕机，需要通过 Resolve 阶段回滚或提交，确保元数据一致性。

## 2. `Reconnect` 阶段的 Capabilities 恢复
- **原文问题**：原文提到 Client 汇报 Capabilities。
- **优化建议**：明确指出 Client 在 Reconnect 阶段汇报的 **Caps** 包含了文件打开模式（读/写）、缓存状态和锁信息。MDS 会根据这些 Caps 重建 **`Capability`** 结构体，并决定是否授予客户端继续访问的权限。如果客户端无响应，MDS 会将其标记为 `blacklist`，防止脏数据写入。

## 3. `Rejoin` 阶段的 Weak/Strong Rejoin
- **原文问题**：原文提到 WeakRejoin 和 StrongRejoin。
- **优化建议**：详细说明：
  - **`WeakRejoin`**：恢复中的 MDS 向其他 MDS 声明自己已经恢复了哪些主数据（Auth）。
  - **`StrongRejoin`**：其他 MDS 回复自己持有的副本数据和锁状态。
  - 这种双向交换确保了恢复后的 MDS 不仅拥有自己的主数据，还知道其他节点持有的副本，从而正确设置 **`replica_map`** 和失效边界。

## 4. 现代 Ceph 的 `standby-replay` 模式
- **原文问题**：原文提到 Standby 接管。
- **优化建议**：补充说明现代 Ceph 支持 **`standby-replay`** 模式。在这种模式下，Standby MDS 会实时 Replay 活跃 MDS 的 Journal。当活跃 MDS 宕机时，Standby 可以几乎瞬间接管（跳过 Replay 阶段），极大缩短故障恢复时间（FRT）。这是生产环境中推荐的高可用配置。

## 5. 源码位置
- **优化建议**：MDS 恢复状态机位于 `src/mds/MDSRank.cc` 的 `handle_mds_map` 函数。`Resolve`、`Reconnect`、`Rejoin` 的具体逻辑分别位于 `src/mds/MDCache.cc` 和 `src/mds/Server.cc` 中。
