# 36. truncate_seq 与截断操作乱序保护机制

本节探讨 Ceph 对象元数据中的核心字段 `truncate_seq` 及其在处理对象截断（Truncate）操作时的关键作用。

## 1. 什么是 truncate_seq？

`truncate_seq`（截断序列号）是存储在对象元数据（`object_info_t`）中的一个单调递增整数。它专门用于标记该对象经历的**截断（Truncate）操作的版本号**。

每次对象执行有效的截断操作时，`truncate_seq` 的值就会加 1。

## 2. 为什么需要它？（乱序保护）

在分布式系统中，由于网络延迟、客户端重试或高并发环境，Op 的到达顺序可能与发送顺序不一致。对于写操作，我们通常通过 Log 和 Version 来保序，但对于改变对象大小（`size`）的截断操作，`truncate_seq` 提供了额外的保护。

它的核心作用是**防止“过期的截断请求”误删“新写入的数据”**。

### 2.1. 典型场景举例

假设一个对象的初始长度为 `1MB`，当前的 `truncate_seq = 10`。

1.  **Op A (新写入)**：客户端向对象写入 `500KB` 数据。
2.  **Op B (新截断)**：客户端请求将对象扩展到 `1.2MB`。OSD 处理成功，更新 `truncate_seq = 11`。
3.  **Op C (迟到旧请求)**：由于网络阻塞，客户端之前发出的一个**旧截断请求**（要求将对象截断到 `800KB`，携带参数 `truncate_seq = 10`）**迟到了**。

**风险分析：**
*   如果没有 `truncate_seq` 校验：OSD 盲目执行 Op C，将对象截断到 `800KB`，此时 **Op B 新写入的 `400KB` 数据将直接被丢弃**。
*   有了 `truncate_seq` 校验：OSD 对比旧请求的 `req.seq (10)` 与对象当前的 `obj.seq (11)`。

### 2.2. 处理规则
在 `do_osd_ops` 处理 `CEPH_OSD_OP_TRUNCATE` 时：

| 比对条件 | 判定 | 动作 |
| :--- | :--- | :--- |
| **`req.seq > obj.seq`** | **新请求** | 执行截断，更新 `size`，并将 `obj.seq` 增加。 |
| **`req.seq < obj.seq`** | **旧请求 (Stale)** | **直接丢弃**，保护现有数据不被覆盖。 |
| **`req.seq == obj.seq`** | **同批次请求** | 通常比较 `size` 大小或按事务流处理。 |

## 3. 总结
`truncate_seq` 就像是为对象的“剪刀手（截断操作）”打上的时间戳。无论网络如何乱序，只有版本号最新的裁剪指令才会生效，这是 Ceph 保障对象长度变更强一致性的重要护栏。
